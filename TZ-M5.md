# ТЗ M5 — Планировщик рациона, оптимизатор закупки, LLM-слой

## Цель
Главная бизнес-логика: по запросу семьи собрать рацион на N дней (рецепты по
дням/приёмам пищи с учётом калоража каждого), посчитать, что купить, минимизируя
остатки, с учётом уже лежащего в «холодильнике». LLM — заменяемая прослойка,
без неё система работает через параметры из кнопок/форм.

## Зависимости
M1 (все таблицы плана), M2 (поиск рецептов), M3 (цены/наличие), M4 (нормы и КБЖУ).

## Состав работ

### 1. Абстракция LLM-провайдера (`app/planner/llm/`)
```python
class LLMProvider(Protocol):
    async def parse_request(self, text: str, context: dict) -> PlanParams: ...
    async def explain_plan(self, plan: Plan) -> str: ...

class NoLLMProvider:      # кнопочный режим, PlanParams приходят из формы мастера (M6)
class OllamaProvider:     # http://ollama:11434, модель qwen3:8b, JSON-mode/grammar
class ClaudeProvider:     # опционально, через ANTHROPIC_API_KEY
```
- `PlanParams`: days(3|4), budget_kop|None, exclude_ingredients[],
  prefer_tags[], meals_per_day, store|None (зафиксировать магазин;
  None — сравнить все и рекомендовать лучший).
- `OllamaProvider.parse_request` — промпт с чётким форматом ответа (JSON schema
  в системном промпте, structured output через Ollama `format: json`);
  на выходе валидировать pydantic-моделью, при ошибке парсинга — retry 1 раз,
  затем fallback на уточняющий вопрос пользователю (не падать молча).
- `explain_plan` — по готовому плану сформировать 3–5 предложений человеческим
  языком: что готовим, почему так закуплено, что доедаем из холодильника.
  Тоже опционально — без LLM страница плана M6 просто показывает данные
  без текста-объяснения.
- Переключение провайдера — одной переменной `.env` `LLM_PROVIDER`, без правки кода.
- M7 расширяет протокол методом `parse_food(text)` (разбор свободного текста
  о съеденной еде в список ингредиент+граммы); `NoLLMProvider` возвращает
  NotSupported — UI открывает ручную форму ввода.
- Модель Ollama — `.env` `OLLAMA_MODEL` (default `qwen3:8b` ≈5.2 ГБ, целиком
  влезает в 8 ГБ VRAM). При подключении LLM-части — мини-бенчмарк на наших
  задачах (валидный JSON из parse_request, связный РУССКИЙ explain_plan,
  латентность <15 с). Кандидаты под железо (8 ГБ VRAM, 24 ГБ ОЗУ;
  qwen3:30b-a3b НЕ влезает): qwen3:8b (весь на GPU, базовый) vs
  qwen3:14b Q4 (≈9 ГБ, гибрид GPU+CPU) vs gpt-oss:20b (открытая MoE от
  OpenAI, ≈13 ГБ, активных 3.6B — терпимо быстра в гибриде; русский слабее
  Qwen — проверить отдельно). Перед бенчмарком свериться с ollama.com/library:
  могли выйти новые модели. Учесть лимит памяти WSL2 для контейнеров
  (`.wslconfig`). Выбрать самую мощную, укладывающуюся в латентность;
  качество русского — обязательный критерий.

### 2. Подбор блюд (`app/planner/select.py`)
Вход: параметры (M4 нормы по членам семьи + PlanParams), холодильник (M1 `fridge`).
1. Жёсткие фильтры (аллергии, excluded, meal_type) → M2 `search_recipes`.
2. Мягкое ранжирование: похожесть на понравившееся (пока нет истории лайков —
   просто relevance из RAG) − штраф за dislikes − бонус за использование того,
   что уже в холодильнике.
3. Разнообразие: не повторять один и тот же рецепт в пределах плана;
   не более 2 раз одна и та же категория подряд.
4. Собрать сетку `дни × приёмы пищи` кандидатами (по 1 основному + 1-2 запасных
   на случай, если оптимизатор закупки завернёт вариант как невыгодный).

### 3. Оптимизатор закупки (`app/planner/purchase_optimizer.py`)
Задача: дана сетка рецептов с граммовками на ингредиент, есть остатки в
холодильнике, есть предложения магазинов (M3, несколько сетей, разные упаковки
и цены) — минимизировать: **траты + вес выброшенных остатков**, с бюджетным
ограничением.

Режим закупки — **один магазин**: ездить за маслом в одну сеть, а за картошкой
в другую — неудобно. Оптимизатор решает задачу независимо для каждого магазина
из `STORES` (только его цены и упаковки) и сравнивает итоги; выигравший —
рекомендация, в M6 показываются суммы по всем магазинам, пользователь может
выбрать другой. Ингредиент, отсутствующий в магазине, делает рецепт
невыполнимым в этой корзине — тогда select.py подбирает замену блюда
(до 2 итераций, как с бюджетом).

- Реализация: Google OR-Tools CP-SAT.
  - Переменные: сколько упаковок каждого предложения купить (int ≥0).
  - Ограничение: сумма (упаковки×граммовка + остаток в холодильнике) ≥
    суммарная потребность ингредиента по плану.
  - Целевая функция: `Σ цена*упаковки + λ*Σ излишек_грамм` (λ — вес штрафа
    за выброс, конфигурируемый, по умолчанию — «излишек дороже, чем он бы стоил
    по цене за грамм», чтобы не покупать 5 кг ради 50 г).
  - Мягкий бюджет: если бюджет задан и решение его превышает — либо ослабить
    (предупредить пользователя), либо запустить select.py заново с более
    дешёвыми рецептами-кандидатами (до 2 итераций).
- Fallback без OR-Tools (на случай проблем с солвером): жадный алгоритм —
  для каждого ингредиента взять минимальный набор упаковок, покрывающий
  потребность с минимальным остатком; хуже глобально, но работает всегда.
  Оба пути — за одним интерфейсом `optimize(demand, fridge, offers, budget)`.
- Остаток после закупки (упаковка − использовано) записывается в план как
  «прогноз пополнения холодильника» — подтверждается пользователем в M6 после
  реальной готовки (мог доесть иначе).

### 4. Оркестрация (`app/planner/service.py`)
`create_plan(family_id, raw_text|PlanParams) -> Plan`:
1. LLMProvider.parse_request (или готовые params из кнопок).
2. family_daily_needs (M4) на все дни плана.
3. select.py → сетка рецептов-кандидатов.
4. Порции на каждого едока (M4 `portion_for`).
5. Суммарная потребность по ингредиентам → M3 `get_offers` по каждому
   магазину → purchase_optimizer на магазин → сравнение корзин → выбор
   магазина (рекомендация или store из params) → список покупок с ценами.
6. Сохранить `meal_plans`, `plan_meals`, `shopping_items` (status=draft).
7. LLMProvider.explain_plan → текст для страницы плана.
8. Пользователь подтверждает (кнопка «Подтвердить план» в M6) → status=active.

## Критерии готовности
- [ ] `create_plan` для тестовой семьи из 3 человек на 4 дня отрабатывает
      <15 сек с Ollama, <5 сек в NoLLM-режиме.
- [ ] Оптимизатор на контрольном кейсе (известные наперёд граммовки и упаковки)
      даёт математически корректный минимум — тест с ручным пересчётом.
- [ ] Сравнение магазинов: на синтетическом кейсе, где одна сеть дешевле по
      корзине целиком, рекомендуется именно она; заданный store в PlanParams
      отключает сравнение.
- [ ] Аллергия/exclude никогда не попадает в план (тест — 100% фильтрация,
      это не полагается на LLM).
- [ ] Смена `LLM_PROVIDER=none→ollama→claude` не требует правок кода, только `.env`.
- [ ] Отказ Ollama (недоступен/таймаут) не роняет создание плана — деградация
      до уточняющего вопроса пользователю или ошибки с понятным текстом.
