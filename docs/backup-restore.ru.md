# Резервное копирование и восстановление

> English version: [backup-restore.md](backup-restore.md)

## Как это устроено

Контейнер `scheduler` каждую ночь в 04:30 (по `APP_TIMEZONE`) делает `pg_dump` в
custom-формате и кладёт результат в том Docker `backups`. Время выбрано **после**
ночного парсинга цен в 03:00, чтобы дамп содержал свежие цены.

Порядок действий в `app/core/backup.py`:

1. Дамп пишется в `*.dump.part`.
2. Архив проверяется командой `pg_restore --list` — она читает только оглавление,
   стоит копейки и ловит обрыв записи. Бэкап, который ни разу не прочитали, —
   это слух, а не бэкап.
3. Только после успешной проверки файл переименовывается в `*.dump`. Благодаря
   этому ротация видит исключительно завершённые файлы, и прерванный дамп
   никогда не приведёт к удалению хорошего.
4. При заданном `BACKUP_DIR` копия отправляется туда — тем же приёмом с
   переименованием (критично для SMB, где копирование может зависнуть на минуты).
5. Ротация оставляет `BACKUP_KEEP` (по умолчанию 14) самых свежих дампов
   **в обоих местах**. Сортировка идёт по имени файла: штамп `ГГГГММДД-ЧЧММСС`
   сортируется лексикографически так же, как хронологически, поэтому результат
   не зависит от того, насколько честные метки времени отдаёт NAS.

Сбой резервного копирования не роняет планировщик: ошибка логируется, процесс
продолжает работать.

### Догоняющий запуск

Обычная запись в cron на домашнем ПК просто **никогда не срабатывает**, если
компьютер выключают на ночь. Это выясняется через три месяца, когда бэкап
понадобился. Поэтому сделано две вещи:

- `misfire_grace_time = 6 часов` и `coalesce=True` — задача отработает, если
  компьютер включили с опозданием;
- при старте планировщика проверяется возраст самого свежего дампа, и если он
  старше 24 часов, бэкап делается сразу.

### Почему `pg_dump` живёт в образе приложения

`pg_dump` не должен быть новее той версии, куда вы когда-нибудь будете
восстанавливать дамп: PostgreSQL 17 поменял версию формата custom-архива, и
`pg_restore 16` такой файл отвергает. В Debian bookworm в основном репозитории
есть только `postgresql-client-15`, который откажется дампить сервер 16. Поэтому
в образ ставится ровно `postgresql-client-16` из репозитория PGDG.

Восстановление, наоборот, выполняется **внутри контейнера `db`** — там версия
клиента совпадает с сервером по построению, а том `backups` уже примонтирован
туда в режиме только для чтения.

## Копия на NAS

Дампы всегда лежат в томе `backups`. `BACKUP_DIR` задаёт **второе** место — как
путь *внутри контейнера*.

SMB-шару NAS нельзя примонтировать в контейнер обычным bind-mount: при бэкенде
WSL2 буква сетевого диска и UNC-путь Windows контейнеру недоступны. Шару
монтирует сам Linux, для этого есть готовый оверлей:

```powershell
# .env
BACKUP_DIR=/mnt/nas-backup
NAS_HOST=192.168.1.50
NAS_SHARE=backups
NAS_USER=ration
NAS_PASSWORD=...

docker compose -f docker-compose.yml -f docker-compose.nas.yml up -d
```

Параметры `uid=10001,gid=10001` в `docker-compose.nas.yml` обязаны совпадать с
пользователем `app` из образа, иначе процесс без прав root не сможет писать.

> **На NAS отправляются только готовые файлы дампов.** Каталог данных Postgres
> обязан оставаться на локальном диске: сетевые файловые системы не дают честных
> файловых блокировок, и размещение `PGDATA` на шаре — надёжный способ повредить
> базу.

## Восстановление

```powershell
.\scripts\restore.ps1 -List                              # что вообще есть
.\scripts\restore.ps1 -Dump ration-20260728-043000.dump  # из тома backups
.\scripts\restore.ps1 -Dump 'D:\c-nas\ration-20260701-043000.dump'  # с диска
```

Скрипт останавливает `api` и `scheduler`, пересоздаёт базу
(`DROP DATABASE ... WITH (FORCE)` — без `FORCE` удаление зависнет за случайным
соединением), восстанавливает дамп, печатает контрольные значения (список
расширений, ревизию Alembic, количество записей) и снова запускает сервисы,
дождавшись ответа от `/health`.

**Это разрушающая операция.** Без ключа `-Yes` скрипт требует ввести имя базы
вручную.

### Проведите учебное восстановление один раз

Критерий готовности ТЗ-M1 включает проверенное восстановление. Путь
восстановления, который ни разу не проходили, не существует. Безопасный способ
потренироваться: создать отдельную базу, восстановить дамп в неё и сравнить
количество строк.
