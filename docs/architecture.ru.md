# Архитектура

> English version: [architecture.md](architecture.md)

## Два принципа

1. **Вся математика — детерминированный код.** Калории, БЖУ, ужарка, размер
   порции, оптимизация закупки. LLM — тонкая съёмная прослойка, которая делает
   ровно две вещи: превращает свободный текст в `PlanParams` и превращает
   готовый план в человеческий текст. Приложение обязано полностью работать при
   `LLM_PROVIDER=none`. **Аллергии и исключения — это SQL-фильтры**, никогда не
   порог похожести и никогда не решение модели.
2. **API-first.** Веб-интерфейс — один из клиентов REST API. Телеграм-бот или
   мобильное приложение добавляются как ещё один тонкий клиент, без переписывания
   ядра.

## Процессы

```
┌── ПК (Windows + Docker Desktop, WSL2) ─────────────────────────────┐
│                                                                     │
│  Браузер ── 127.0.0.1:8000 ──► [api]  FastAPI + uvicorn             │
│                                  │                                  │
│                                  ├── /api/v1/*   REST               │
│                                  ├── /docs       Swagger UI         │
│                                  ├── /health     проба              │
│                                  └── /*          SPA (с M6)         │
│                                  │                                  │
│  [scheduler]  APScheduler ───────┤                                  │
│    03:00 сбор каталогов (M3)     │                                  │
│    04:30 бэкап БД (M1)           ▼                                  │
│                            [db]  PostgreSQL 16 + pgvector           │
│                                                                     │
│  [ollama]  qwen3:8b на GPU ◄── LLMProvider (съёмный слой, M5)       │
│  [ollama-init]  разовая загрузка модели, завершается кодом 0        │
└─────────────────────────────────────────────────────────────────────┘
```

Контейнеры `api` и `scheduler` — это **один образ с разными командами запуска**.
Единственная разница в поведении задаётся переменной `RUN_MIGRATIONS`: миграции
применяет только `api`, а `scheduler` ждёт, пока схема появится.

## Слои кода

```
app/
├── core/            фундамент, от которого зависят все
│   ├── config.py      настройки (pydantic-settings)
│   ├── clock.py       «какое сегодня число» в часовом поясе семьи
│   ├── db.py          движок, фабрика сессий, зависимость get_session
│   ├── models/        общее ядро схемы: только структура, никакой логики
│   ├── errors.py      иерархия AppError + единый конверт ответа
│   ├── logging.py     structlog
│   ├── middleware.py  request-id и журнал доступа
│   ├── http.py        общий httpx-клиент с таймаутами
│   ├── backup.py      pg_dump, проверка, копирование, ротация
│   └── spa.py         шов между M1 и M6 для раздачи статики
├── api/v1/          только роутеры, без бизнес-логики
├── recipes/         M2   поиск, эмбеддинги, нормализация
├── store/           M3   адаптеры магазинов, матчинг, цены
├── nutrition/       M4   формулы норм и КБЖУ
├── planner/         M5   подбор блюд, оптимизатор закупки, llm/
├── finance/         M7   дневник, траты, аналитика
└── scheduler/       процесс APScheduler и его задачи
```

**Правило слоёв:** `app/core/models` — общее ядро. Пакеты модулей импортируют
из него, но не наоборот. Это не вкусовщина: `alembic/env.py` делает
`from app.core.models import Base`, и если бы модели жили в пакетах модулей,
процесс миграции тянул бы роутеры FastAPI, `sentence-transformers` и `ortools`.

## Жизненный цикл запроса

1. `RequestContextMiddleware` заводит `request_id` (или берёт его из заголовка
   `x-request-id`) и кладёт в контекст structlog. Дальше **каждая** строка лога
   в любом модуле несёт его без передачи через аргументы функций.
2. Роутер из `app/api/v1/` разбирает запрос, pydantic валидирует вход.
3. Зависимость `get_session` выдаёт сессию SQLAlchemy. Обработчики фиксируют
   транзакцию **явно** — неявный commit молча сохранял бы половину работы у
   обработчика, вышедшего раньше времени.
4. Ошибки превращаются в конверт `{"error": {"code", "message", "details"}}`
   обработчиками из `app/core/errors.py`.
5. Middleware дописывает `x-request-id` в ответ и пишет строку журнала доступа
   с длительностью.

## Что происходит при старте

`create_app()` **намеренно не подключается к базе.** `create_async_engine`
соединение не открывает; первое реальное подключение случается на первом
запросе. Благодаря этому сбой базы оставляет контейнер поднятым, а `/health`
честно отвечает `degraded` — вместо цикла перезапусков под
`restart: unless-stopped`.

Порядок запуска в Compose: `db` → (healthy) → `api` (миграции, затем uvicorn) →
(healthy) → `scheduler`. Ollama не блокирует ничего: `api` стартует независимо, а
загрузка модели идёт в отдельном одноразовом контейнере.

После перезагрузки Windows Docker поднимает контейнеры **по политике
restart и игнорирует `depends_on`**. Поэтому entrypoint в любом случае ждёт базу
сам, а `scheduler` ещё и ждёт появления схемы; в `alembic/env.py` вдобавок стоит
транзакционная advisory-блокировка на случай, если миграции всё же запустятся
одновременно.

## Что зафиксировано сейчас ради M6

- Все роутеры модулей существуют и зарегистрированы под `/api/v1`, даже пустые:
  URL-пространство и теги OpenAPI стабильны с первого коммита.
- `generate_unique_id_function` даёт читаемые и устойчивые `operationId`.
  По умолчанию было бы `search_recipes_api_v1_recipes_search_get`, и имя менялось
  бы при каждом изменении URL — то есть генерируемые типы фронтенда переписывались
  бы на ровном месте.
- `separate_input_output_schemas=False`: иначе каждая модель с значениями по
  умолчанию распадается на `FooInput`/`FooOutput` и удваивает генерируемый
  TypeScript без всякой пользы.
- `ErrorResponse` объявлен один раз на уровне роутера, поэтому в схеме он
  окажется одним общим типом, а не копией на каждый эндпоинт.
- `mount_spa()` уже вызывается последним и сам выбирает ветку: пока `web/dist`
  нет — отдаёт заглушку, как только появится — раздаёт SPA. В M6 не придётся
  трогать `main.py`.
