# Разработка

> English version: [development.md](development.md)

## Окружение

Инструмент — [uv](https://docs.astral.sh/uv/). Если его нет, ставится одной
командой: `python -m pip install uv` (тогда вместо `uv ...` пишите
`python -m uv ...`).

```powershell
uv sync            # окружение разработчика: зависимости + группа dev
uv run pytest -q
uv run ruff check . ; uv run ruff format . ; uv run mypy
```

Проект «виртуальный»: `[tool.uv] package = false`, то есть uv ставит только
зависимости и никогда не собирает сам `app`. Благодаря этому слой зависимостей
в Docker не зависит от исходников — правка кода не инвалидирует кеш сборки.
Плата за это — `PYTHONPATH=/app` в образе и `pythonpath = ["."]` в настройках
pytest.

Файл `uv.lock` **коммитится**. Он разрешает зависимости сразу для всех
платформ, поэтому «работает на Windows» и «работает в контейнере» не могут
разойтись. Обновить одну зависимость: `uv lock --upgrade-package fastapi`.

### Почему torch берётся с отдельного индекса

`sentence-transformers` (M2) тянет torch. Обычная сборка torch с PyPI под Linux
весит 526 МБ и тащит за собой ~2.5 ГБ пакетов `nvidia-*`, которые проекту не
нужны никогда: эмбеддинги считаются на процессоре, а видеокарта отдана Ollama в
отдельный контейнер. Поэтому в `pyproject.toml` есть

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = [{ index = "pytorch-cpu" }]
```

Это уже разрешено в `uv.lock`, поэтому подключение M2 — пересборка образа, а не
повторное разрешение зависимостей.

## Режим разработки

```powershell
.\scripts\dev.ps1
```

Скрипт поднимает `db` (и `ollama`) в Docker, а само приложение запускает на
Windows с `--reload`. Причина: перезагрузчик uvicorn опирается на нативные
события файловой системы, а через границу Windows → WSL2 они доставляются
ненадёжно — в контейнере hot reload вырождается в опрос с высокой нагрузкой на
процессор либо просто пропускает правки. Дополнительный выигрыш: продовому
compose-файлу не нужен bind-mount исходников, а значит снимается весь класс
проблем с кириллицей в пути.

`.env` при этом **не меняется**: в нём лежит вариант для Docker (`@db:5432`), а
скрипт подставляет хостовый через переменные окружения процесса —
pydantic-settings ставит их выше файла. Отдельный `.env.dev` разошёлся бы за
неделю.

Полезные ключи: `-NoOllama` (не поднимать Ollama), `-ResetDb` (пересоздать базу;
намеренно не `docker compose down -v`, который снёс бы и 5-гигабайтный том с
моделью), `-Port`.

## Тесты

```powershell
docker compose up -d db      # нужен один раз
uv run pytest -q
```

Тестовая база — отдельная база `ration_test` **внутри того же контейнера**, а не
одноразовый контейнер. На Docker Desktop/WSL2 запуск контейнера съедает всё
время: переиспользование уже прогретого Postgres даёт старт набора меньше чем за
секунду вместо десяти, и это разница между «тесты гоняют» и «тесты не гоняют».

Схема создаётся один раз за сессию через `alembic upgrade head`, а не
`metadata.create_all()`: последний пропустил бы `CREATE EXTENSION` и сиды и
никогда не проверял бы ту миграцию, которая работает в проде. Каждый тест
оборачивается во внешнюю транзакцию и откатывается; `join_transaction_mode="create_savepoint"`
позволяет тестируемому коду свободно вызывать `commit()`.

Тесты, помеченные `@pytest.mark.db`, пропускаются, если Postgres недоступен.

## Миграции

Все таблицы уже созданы миграцией `0001`. Новая миграция нужна только если модуль
действительно добавляет таблицу или колонку.

```powershell
uv run alembic revision --autogenerate -m "описание"
uv run alembic upgrade head
uv run alembic check      # модели и миграции сходятся?
```

`alembic check` — самая ценная проверка в наборе: она утверждает, что модели и
миграции согласованы, а это первый инвариант, который портится, когда модули
начинают добавлять колонки. Он же входит в CI.

Автогенерация **не умеет**: создавать расширения, замечать изменения в CHECK-ограничениях,
вставлять сиды. Всё это правится руками, как в `0001`.

## Стиль

- Код, идентификаторы, докстринги, комментарии, сообщения коммитов и имена
  событий в логах — **по-английски**. Строки интерфейса — по-русски.
- Правила линтера и типов — в `pyproject.toml`. mypy запущен в режиме `strict`.
- Правила `RUF001–RUF003` (неоднозначные символы) отключены: интерфейс на
  русском, и кириллица в строках — это норма.
- В логах используйте структурные вызовы: `log.info("plan.created", plan_id=7,
  store="lenta")`, а не форматирование строк. `request_id` подставляется сам.

## Ветки и коммиты

Ветка на модуль: `feat/m1-core`, `feat/m2-recipes`, … Слияние в `main` после
того, как критерии готовности из ТЗ проверены фактически. Сообщения коммитов —
английские, в формате Conventional Commits со скоупом по имени пакета
(`core`, `api`, `db`, `recipes`, `store`, `planner`, `finance`, `web`, `docker`).

CI (`.github/workflows/ci.yml`) на каждый push и PR гоняет ruff, mypy, pytest с
контейнером pgvector, цикл `upgrade → downgrade → upgrade` и сборку образа.

## Известные ограничения окружения (актуально к M6)

- **Node 22.12 на хосте уже мал.** `eslint@10` требует `^22.13`,
  `react-router@8` — `>=22.22`. Перед M6 обновите Node до 24 LTS.
- **React 18 из README конфликтует с актуальными библиотеками.** `@mantine/core@9`
  требует `react ^19.2`, `react-router@8` — `react >=19.2.7`. Остаться на React 18
  означает сразу зафиксировать две библиотеки на предыдущих мажорных версиях.
  Решение принимать в M6.
- **`openapi-typescript@7` объявляет peer-зависимость `typescript ^5`**, поэтому
  во фронтенде придётся зафиксировать TS 5.9, а не 7.
