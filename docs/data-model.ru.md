# Модель данных

Схема живёт в `app/core/models/` и целиком создаётся одной миграцией
`alembic/versions/0001_initial_schema.py` — так требует ТЗ-M1: «все таблицы
проекта создаются здесь, чтобы модули не конфликтовали миграциями».

> English version: [data-model.md](data-model.md)

## Слои

`app/core/models` — **общее ядро схемы: только структура, никакой логики.**
Пакеты модулей (`app/recipes/`, `app/store/`, `app/nutrition/`, `app/planner/`,
`app/finance/`) держат запросы и сервисы и импортируют отсюда — никогда наоборот.
Это не эстетика: `alembic/env.py` делает `from app.core.models import Base`, и
если бы модели лежали в пакетах модулей, процесс миграции тянул бы за собой
роутеры FastAPI, `sentence-transformers` и `ortools`.

| Файл | Таблицы |
|---|---|
| `base.py` | `Base`, соглашения об именах, словарь типов, миксины меток времени |
| `enums.py` | закрытые словари + `pg_enum()` |
| `json_shapes.py` | Pydantic-модели для каждой JSONB-колонки |
| `reference.py` | `ingredient_categories`, `cook_coefficients` |
| `family.py` | `families`, `family_members`, `weight_log` |
| `recipes.py` | `ingredients`, `recipes`, `recipe_ingredients` |
| `store.py` | `store_products`, `price_history`, `parse_runs` |
| `planning.py` | `meal_plans`, `plan_meals`, `plan_meal_portions`, `shopping_items`, `fridge` |
| `diary.py` | `meal_log`, `expenses` |

## Сквозные соглашения

- **Деньги** — `INTEGER` в копейках, имена колонок кончаются на `_kop`.
- **Количества** — `NUMERIC`, в Python это `Decimal`. Причина та же, что у
  копеек: ТЗ требует точных чисел (ужарка мяса даёт ровно 252 г из 400 г, КБЖУ
  сходится с точностью ±2%). `float` этого не гарантирует. В `int` переводим
  только на двух границах: CP-SAT в M5 и сериализация JSON.
- **Моменты времени** — `TIMESTAMPTZ`. **Календарные даты** — `DATE`, и
  вычисляются через `app/core/clock.py`, а не `date.today()`: контейнер живёт в
  UTC, а парсер магазинов запускается в 03:00 по Москве, когда в UTC ещё вчера.
- **Закрытые словари** — `VARCHAR(32)` + именованный CHECK, зеркалом к
  `StrEnum` в Python. Нативные ENUM'ы Postgres не используем: Alembic не умеет
  находить разницу в списке значений, а `ALTER TYPE ... ADD VALUE` нельзя
  выполнить в той же транзакции, где значение используется.
- **Колонки `store`** — обычный `TEXT` **без** CHECK. Набор магазинов задаётся
  переменной `STORES` и наличием реализаций `StoreAdapter`; ограничение здесь
  означало бы миграцию на каждую новую сеть.
- **JSONB** всегда присваивается целиком из модели в `json_shapes.py` —
  SQLAlchemy не отслеживает изменения словаря на месте.

## Векторный поиск

Три колонки `VECTOR(384)` — `recipes.embedding`, `ingredients.embedding`,
`store_products.embedding` — с HNSW-индексами по `vector_cosine_ops`.

- Расширения `vector` и `pg_trgm` создаёт **миграция**. Образ
  `pgvector/pgvector:pg16` только кладёт файлы расширения на диск, но
  `CREATE EXTENSION` не выполняет — это проверено на чистом томе.
- Параметры: `m=16, ef_construction=64` для рецептов и ингредиентов (тысячи
  строк); `m=24, ef_construction=100` для товаров магазинов (десятки тысяч, и
  от полноты выдачи там напрямую зависит критерий M3 «точность автоматических
  связок ≥90%»).
- **Никакого `register_vector`.** Тип pgvector для SQLAlchemy передаёт вектор
  строкой; если зарегистрировать бинарный кодек asyncpg, слои начнут спорить.
  Тест `test_vector_column_round_trips_through_asyncpg` это стережёт.
- Строки с `embedding IS NULL` в HNSW-индекс не попадают и в выдаче не
  появляются — это корректно (рецепт без эмбеддинга не ищется), но означает,
  что прогресс `backfill_embeddings` виден как охват поиска.
- **Важно для M2:** при приблизительном индексе фильтры применяются **после**
  обхода индекса. Жёсткий фильтр аллергий может выкинуть почти всех кандидатов,
  и вместо 20 результатов вернётся 2. Лечится на уровне запроса:
  `SET LOCAL hnsw.iterative_scan = strict_order` (pgvector ≥0.8, в образе 0.8.5).

## Отклонения от SQL-наброска ТЗ-M1

Набросок в ТЗ-M1 §2 — эскиз, а не DDL. Ниже полный список изменений с
причинами. Каждое можно откатить, но большинство из них — прямые блокеры для
модулей M2–M7, а ТЗ само требует решить это в M1.

### Отсутствовало то, без чего модуль нереализуем

| Таблица | Что добавлено | Почему |
|---|---|---|
| `meal_plans` | `start_date DATE NOT NULL` | `plan_meals.day` — относительный номер дня. Ничто не связывало план с календарём, а дашборд M6 показывает «блюда сегодняшнего дня», дневник M7 пишется по датам и сравнивает план с фактом |
| `meal_plans` | `store TEXT` | Вся суть M5 — закупка в одном магазине; оптимизатор сравнивает корзины и выбирает победителя. Решение было негде записать |
| `meal_plans` | `basket_comparison JSONB` | Шаг 3 мастера M6 рисует суммы по всем магазинам, включая проигравшие. Без хранения страницу нельзя переоткрыть, не перезапустив CP-SAT |
| `meal_plans` | `explanation TEXT` | Результат `LLMProvider.explain_plan`. Иначе каждый показ страницы — это вызов Ollama на 15 секунд, и страница ломается, когда Ollama недоступна |
| `meal_log` | `plan_meal_id FK` | Первый же эндпоинт M7 — `POST /diary/plan-meal {plan_meal_id, ...}`. По одному `recipe_id` нельзя отличить, какой именно слот съеден (один рецепт может стоять и на день 1, и на день 3) |
| `meal_log` | `items JSONB` | M7 разбирает свободный текст в список ингредиентов и требует «редактирование и удаление записей». Хранение только четырёх итоговых чисел делает правку невозможной |
| `expenses` | `store_product_id`, `qty`, `store` | «Ручная покупка из каталога → запись в expenses **И** пополнение холодильника» — у второй половины операции не было источника истины |
| `families` | `meal_split JSONB` | M4: «распределение по приёмам пищи конфигурируемо на семью». Места не было |
| `ingredients` | `density_g_per_ml`, `piece_grams` | M2 переводит «2 шт» и «стакан» в граммы, M3 — «0,93 л». Без плотности 0,93 л масла превращаются в 930 г вместо ~856 г: систематическая ошибка в ранжировании по цене за грамм |
| `store_products` | `match_status`, `candidate_ingredient_id`, `match_source`, `matched_at` | M3 определяет три исхода матчинга, включая **очередь ручного подтверждения**, а M6 — админ-страницу с кнопками «да/нет». Старая схема не различала «связано автоматом», «кандидат» и «человек отклонил», поэтому отклонённые пары предлагались бы заново каждую ночь и очередь никогда не пустела бы |
| `recipes` | `status`, `quarantine_reason` | M2 отправляет в карантин рецепты с >30% ненормализованных строк, M6 показывает их в админке. Флага не было |
| `plan_meals` | `alternates JSONB` | M5 подбирает «1–2 запасных», M6 даёт кнопку «заменить блюдо». Запасные негде было хранить |

### Структурные исправления

| Таблица | Было | Стало | Почему |
|---|---|---|---|
| `recipe_ingredients` | PK `(recipe_id, ingredient_id)` | суррогатный `id` + `UNIQUE (recipe_id, position)` | Составной ключ запрещал один ингредиент дважды в рецепте. «Масло в тесто» + «масло смазать форму» — обычное дело, импортёр либо падал бы, либо молча терял вторую строку |
| `recipe_ingredients` | `ingredient_id NOT NULL` | nullable + `raw_text`, `raw_amount`, `raw_unit` | M2 отправляет в карантин только рецепты с >30% нераспознанных строк — значит рецепт с 20% обязан сохраняться, и его нераспознанным строкам нужно место. Исходный текст сохраняем, чтобы перезапускать нормализацию без повторного парсинга 5000 страниц |
| `plan_meals` | `portions JSONB {member_id: множитель}` | таблица `plan_meal_portions` | Ключи JSONB всегда строки, ссылочной целостности нет, а главный отчёт M7 («факт vs норма по каждому члену», «план vs факт») превращался бы в `jsonb_each_text` с приведениями типов в каждом запросе |
| `shopping_items` | `planned_price_kop` | `planned_unit_price_kop` + `actual_qty` | Было неясно, это цена упаковки или сумма строки. Ошибка в трактовке — молчаливое трёхкратное расхождение в проверке бюджета |
| `fridge` | неясно, остаток или партия | партии (lots), плюс `source`, `plan_id` | `expires_at` имеет смысл только для партии: два пакета молока куплены в разные дни. Потребители агрегируют `SUM(grams) GROUP BY ingredient_id` |
| `store_products`, `parse_runs` | `store TEXT DEFAULT '5ka'` | без DEFAULT | Значение по умолчанию в мультимагазинной системе провоцирует молчаливое приписывание товара не той сети |
| `parse_runs` | `running\|ok\|failed` | + `partial`, `error`, `trigger` | Прогон, собравший 8 категорий из 10, — реальное и частое состояние. `stats.errors = 7` не говорит, что чинить, — нужен текст ошибки |
| — | новая таблица `ingredient_categories` | | `ingredients.category` и `cook_coefficients.ingredient_category` были двумя несвязанными текстовыми полями, соединяемыми сравнением строк. Опечатка («овощ» вместо «овощи») давала бы коэффициент 1.0 молча, и M4 рапортовал бы сырой вес как готовый |

### Индексы, которых не было в списке ТЗ

ТЗ называет HNSW и три b-tree индекса. Добавлены (каждый обоснован конкретным
запросом из ТЗ модулей):

- `ix_recipe_ingredients_ingredient_id` — **горячий путь фильтра аллергий** в M2
  и M5. Составной PK из наброска обслуживать поиск по одному `ingredient_id` не
  может, поэтому каждая генерация плана делала бы полный проход по ~50 000 строк.
- `ix_store_products_ingredient_id_store` (частичный) — `get_offers()` в M5
  вызывается по разу на ингредиент **на каждый магазин**: ~120 раз на план из
  4 дней.
- `ix_recipes_meal_type`, `ix_recipes_tags` (GIN) — обязательные фильтры поиска M2.
- `ix_expenses_family_id_date` — у `expenses` в ТЗ не было индексов вообще, а
  весь финансовый модуль M7 — это агрегаты по диапазону дат.
- `ix_parse_runs_store_started_at` — дашборд M6 показывает свежесть цен **по
  каждому магазину**; индекс по одному `started_at` такой запрос не обслужит.
- `uq_meal_plans_one_active` (частичный уникальный) — дашборд, покупки и дневник
  говорят «активный план» в единственном числе. Индекс делает это инвариантом.
- `uq_recipes_source_url` — критерий готовности M2 буквально требует
  идемпортентности повторного импорта по `source_url`.
- `uq_meal_log_plan_meal_member` (частичный уникальный) — делает кнопку
  «съедено» идемпотентной: двойное нажатие на телефоне не должно записать
  800 ккал дважды.

### Кэшированные КБЖУ рецепта

ТЗ-M2 §5 разрешает «материализованное поле или на лету» и выбирает «на лету».
Колонки `kcal_per_serving` и соседние всё же добавлены, потому что
`max_kcal_per_serving` — это **фильтр** поиска: считать его на лету означает
агрегировать `recipes ⋈ recipe_ingredients ⋈ ingredients` по всей таблице до
того, как отработает векторная сортировка. Использовать их или нет — решение M2;
колонки nullable и ничего не ломают.

## Политика удаления

- **Каскад** — там, где дочерняя запись без родителя бессмысленна: члены семьи и
  их дневники от семьи, состав рецепта от рецепта, цены от товара, содержимое
  плана от плана.
- **RESTRICT** — там, где удаление испортило бы историю: `plan_meals.recipe_id`,
  `shopping_items.product_id`, `fridge.ingredient_id`.
- **SET NULL** — там, где факт остаётся правдой без ссылки: `expenses.plan_id`
  (потраченные деньги реальны, даже если план удалили), `meal_log.recipe_id`.

Ловушка, которую это создаёт: у `meal_log.member_id` каскад, а не RESTRICT.
Интуиция подсказывает RESTRICT, чтобы случайное удаление члена семьи не стёрло
год дневника, — но `families → family_members` каскадный, и такой RESTRICT
ломал бы удаление семьи с невнятной ошибкой. Поэтому **API никогда не удаляет
члена семьи физически**: `DELETE /api/v1/members/{id}` ставит `is_active = false`.
Так же и с рецептами: `status = 'archived'`, никогда `DELETE`.
