## 1. Почему текущий планировщик плохой

Текущий алгоритм — жадный: на каждый слот заново сортирует всех кандидатов и
берёт верхний. Подтверждённые проблемы (AUDIT §2, блок P):

- P1 `planner.py:727-738` — полная пересортировка кандидатов на каждый слот;
- P2 `planner.py:739` — при нехватке кандидатов молча повторяет одно блюдо;
- P3 `planner.py:730` — кухня — первый ключ сортировки: «мягкое предпочтение»
  из UI на деле доминирует над ценой, разнообразием и всем остальным;
- P4 `planner.py:751` — покупки агрегируются по `(имя, unit)`: «молоко» и
  «молоко 3,2%» — две позиции;
- P5 `planner.py:741` — неизвестные порции молча заменяются на 4: количества и
  цены выдуманы;
- P6 `nutrition.py` — ккал из 35 substring-правил, БЖУ нет;
- P7 `planner.py:21-26,335-340` — аллергия ищется substring-ом по склеенному
  тексту, «овсян» отнесён к глютену, тип правила игнорируется;
- B3 — `target_kcal` собирается и не используется;
- бюджет и запасы (сроки годности) на выбор блюд не влияют вовсе — только
  подсчитываются постфактум.

Вывод: заменить жадный перебор на честную двухфазную схему
«жёсткие фильтры → оптимизация по горизонту».

## 2. Целевая архитектура

```
(1) Кандидаты: SQL-фильтр           review_status='ready', нужный meal_type
(2) Жёсткие ограничения (hard):     аллергии/исключения, техника, лимит времени
(3) Оценка блюда:                   стоимость (Лента/запасы), ккал, теги
(4) ОПТИМИЗАЦИЯ по всему горизонту: CP-SAT (OR-Tools), fallback — жадный
(5) Масштабирование порций          и сборка списка покупок (FEFO из запасов)
```

Новые модули (разбить `planner.py`, каждый со своими тестами):

- `app/web/planning/candidates.py` — фильтры (2) и оценка (3);
- `app/web/planning/optimizer.py` — модель CP-SAT + жадный fallback;
- `app/web/planning/scaling.py` — порции и масштабирование ингредиентов;
- `app/web/planning/shopping.py` — покупки, запасы, упаковки;
- `app/web/planner.py` остаётся тонким фасадом `build_plan(...)` с той же
  сигнатурой для `main.py`/`database.py`.

### 2.1 Кандидаты и жёсткие ограничения

- Базовая выборка: `review_status='ready'`; если таких < 60 — добирать
  `needs_review` с пометкой `draft=true` в ответе (UI показывает бейдж).
- Аллергии/исключения: матчить по `recipe_ingredients.normalized_name` через
  словарь синонимов (новая таблица `app_core.ingredient_synonyms(term TEXT
  PRIMARY KEY, canonical TEXT NOT NULL)`, засеять ~50 строк: молоко/молока/
  молочный→молоко; глютен→пшеница,рожь,ячмень,мука; орех→грецкий орех,фундук,
  миндаль,кешью и т.д.). Убрать «овсян»→глютен. `rule_type='dislike'` — НЕ
  жёсткий фильтр, а штраф в оценке; `allergy`/`intolerance`/`exclude` c
  `is_hard=true` — жёсткий.
- Техника: пустой список у пользователя = не фильтровать (фикс A2).
- Повторяемость: блюдо не может встречаться дважды в одном дне; в пределах
  горизонта — максимум 2 раза, и не в соседние дни (жёсткое ограничение
  модели, не штраф).

### 2.2 Оценка блюда (для целевой функции)

Для каждого кандидата `r` и слота `(день d, приём m)` посчитать один раз:

- `cost_kop(r)` — стоимость ингредиентов по лучшей цене Ленты (карта/акция)
  с учётом покрытия из запасов (что есть дома — бесплатно); ингредиенты без
  сопоставления — медиана стоимости сопоставленных, помеченная
  `cost_estimated=true`;
- `kcal(r)` — по `recipe_nutrition`, если есть (M3); иначе текущая оценка
  `nutrition.py`, честно помеченная `estimated`; отсутствие оценки не
  выбрасывает блюдо;
- `expiry_bonus(r)` — сумма по ингредиентам, чьи synonyms-совпадения лежат в
  запасах со сроком ≤ 4 дней (использовать то, что скоро испортится);
- `dislike_penalty(r)` — число совпадений с нежёсткими правилами;
- `cuisine_bonus(r)` — 1, если кухня в выбранных пользователем, иначе 0;
- `meal_fit(r, m)` — 1, если `m ∈ meal_types`, 0.5 если meal_types пуст.

### 2.3 Модель CP-SAT

Зависимость: `ortools` (закреплённая версия) — добавить в `pyproject.toml`
(основные зависимости) и `Dockerfile.web`. Это выполнение обещания TZ-v2 §10.

Переменные: `x[r,d,m] ∈ {0,1}` — блюдо r в день d на приём m.
Кандидаты на слот — топ-40 по грубой оценке (ограничить размер модели).

Жёсткие ограничения:

- на каждый слот ровно одно блюдо: `Σ_r x[r,d,m] = 1`;
- повторяемость из 2.1: `Σ_m x[r,d,m] ≤ 1`; `Σ_{d,m} x[r,d,m] ≤ 2`;
  `x[r,d,·] + x[r,d+1,·] ≤ 1`;
- бюджет, если задан: `Σ x[r,d,m]·cost_kop(r) ≤ budget_kop` — как
  **мягкое** ограничение с большим штрафом за превышение (иначе легко
  получить infeasible; UI показывает «бюджет превышен на X ₽»);
- дневные калории на семью, если известен target: попадание в ±20% —
  мягкое ограничение со штрафом за отклонение (использовать `target_kcal`
  людей — фикс B3; людей без цели считать по 2000 взрослый / 1400 ребёнок,
  честная константа до M3).

Целевая функция (минимизация, веса — именованные константы в одном месте):

```
  W_COST   · Σ cost_kop / 100
+ W_BUDGET · превышение бюджета (kop/100)
+ W_KCAL   · |отклонение от дневной цели| / 100
+ W_WASTE  · (− Σ expiry_bonus)          # поощряем использование запасов
+ W_VARIETY· Σ повторов пары (главный ингредиент, день±1)
+ W_TASTE  · Σ dislike_penalty
− W_CUISINE· Σ cuisine_bonus
− W_FIT    · Σ meal_fit
```

Стартовые веса: W_COST=1, W_BUDGET=50, W_KCAL=2, W_WASTE=3, W_VARIETY=4,
W_TASTE=5, W_CUISINE=2, W_FIT=3. Лимит решателя: 10 секунд, 4 воркера;
статус (`OPTIMAL`/`FEASIBLE`) — в ответ плана как `solver_status`.

Стратегии «Экономно/Сбалансированно/Премиально» из UI: множитель к W_COST
(3 / 1 / 0.3) плюс для «Премиально» — предпочтение верхнего ценового квартиля
товарных сопоставлений при сборке покупок (как сейчас), не в модели.

Fallback: если `ortools` недоступен (ImportError) или решатель не нашёл
FEASIBLE за лимит — детерминированный жадный алгоритм: слоты по порядку,
кандидаты по той же целевой функции локально; те же жёсткие ограничения
повторяемости (без молчаливых повторов — если кандидатов не хватило, слот
остаётся пустым с причиной `not_enough_recipes`, UI показывает это честно).

### 2.4 Порции и масштабирование

- `scale = required_servings / source_servings`, где `required_servings` =
  Σ `portion_factor` людей (как сейчас), а `source_servings` — из рецепта.
- **Если у рецепта нет servings и нет yield — блюдо не масштабируется**:
  количества показываются «как в книге», план помечает `scale_unknown=true`,
  а покупки для него считаются на 1 базовый рецепт. Молчаливую подмену «4»
  (P5) удалить.
- Ингредиенты с `is_to_taste=true` не масштабируются и в покупки не попадают
  (соль/перец), кроме случая, когда их нет в запасах — тогда одна позиция
  «докупить» без количества.
- Без раннего округления (TZ-M2 §5): масштабированные количества хранить
  Decimal, округлять только при отображении (г/мл — до 5, штучные — вверх до
  целого).

### 2.5 Покупки и запасы

- Агрегация по **canonical-имени** из словаря синонимов (не по сырому имени) +
  совместимой единице (г+кг складываются в г; мл+л — в мл; штучные — в шт;
  несовместимые единицы — отдельные строки).
- Списание запасов FEFO (раньше истекающие — первыми), как сейчас, но по
  canonical-имени.
- Упаковки Ленты: `ceil(need / pack_quantity)`, показывать и количество
  упаковок, и излишек («останется ~120 г»).
- Позиции без товарного сопоставления — отдельная секция «уточнить в магазине»
  (не «цена не найдена» на каждой строке).

## 4. Тесты (дополнить `tests/test_web_planner.py`, новые файлы —
`tests/test_planning_*.py`)

Обязательные, без сети и БД (данные — фикстуры-словари):

1. Аллергия через синоним: правило «орехи» исключает рецепт с «фундук».
2. «Овсянка» НЕ исключается правилом «глютен» без явного синонима.
3. dislike не выбрасывает рецепт, но проигрывает равному без штрафа.
4. Пустая техника пользователя не фильтрует кандидатов.
5. Повторяемость: на горизонте 7 дней ни одно блюдо не чаще 2 раз и не в
   соседние дни (проверить и CP-SAT, и fallback).
6. Бюджет: при жёстко заниженном бюджете план строится, warning о превышении
   присутствует, стоимость минимальна среди допустимых (сравнить с перебором
   на игрушечном наборе из 5 рецептов × 2 дней).
7. Игрушечная оптимальность: 3 рецепта с известными ценами, 1 день — решатель
   выбирает дешёвый при W_COST-доминировании и любимую кухню при
   W_CUISINE-доминировании.
8. scale_unknown: рецепт без порций не масштабируется и помечен.
9. Покупки: «молоко» 300 мл + «молока» 0.5 л → одна позиция 800 мл; г+кг
   складываются; FEFO списывает раньше истекающую партию.
10. Fallback без ortools (ImportError-мок) даёт валидный план без повторов.

Приёмка: `python -m unittest discover -s tests -v` зелёный; ручная проверка —
план на 7 дней для семьи из 3 человек с бюджетом строится ≤ 15 секунд, блюда
не повторяются в соседние дни, список покупок агрегирован по продуктам.
