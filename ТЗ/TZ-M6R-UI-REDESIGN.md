# TZ-M6R — Редизайн веб-интерфейса и фиксы бэкенда

> **Для исполнителя (сессия Claude Code на Opus).** Самодостаточное ТЗ.
> Предпосылка: данные рецептов пересозданы по [TZ-M2R](TZ-M2R-RECIPES-LLM.md)
> (есть структурированные ингредиенты с `is_to_taste`/`section`/`note` и
> рецепты со статусом `ready`). Если TZ-M2R ещё не выполнен — часть А можно
> делать сразу, часть Б лучше после него.
> Планировщик глубоко не переделывать — это [TZ-M5R](TZ-M5R-PLANNER.md);
> здесь только фиксы, без которых UI лжёт пользователю.

## 0. Контекст

Приложение: FastAPI + asyncpg + PostgreSQL 16, SPA без фреймворка
(`app/web/static/index.html` + `app.js` + `styles.css`), 6 экранов: Сегодня,
План питания, Рецепты, Продукты «Ленты», Запасы, Настройки. Docker-сервис
`web` на `127.0.0.1:8080`.

Главные претензии пользователя: интерфейс в целом не нравится; данные (особенно
ингредиенты и списки) выглядят нераздельным месивом. Полный аудит —
[AUDIT-2026-08-16.md](AUDIT-2026-08-16.md) §2.

- [x] **A2. Разблокировать нового пользователя.** При регистрации создавать

      «техника не указана, не фильтровать». Выбрать второе (меньше магии),
      отразить в настройках подсказкой «укажите технику, чтобы уточнить меню».
- [x] **A3. Ингредиенты в списке рецептов.** `list_recipes`
      (`database.py:305-358`): не выбрасывать `ingredient_names` (строка 345),

      `WHERE review_status != 'rejected'` + `ORDER BY (review_status='ready')

      `count(*) OVER()` для пагинации.
- [x] **A4. Эндпоинты, которых не хватает интерфейсу:**
      - `GET /api/plans?limit=20` — история планов (`meal_plans` уже хранит все);
      - `DELETE /api/plans/{id}` — удаление плана;
      - `PATCH /api/plans/{id}/items/{item_id}` — отметка «куплено»
        (новая колонка `plan_ingredients.purchased_at TIMESTAMPTZ NULL`);
      - `POST /api/recipes/{id}/review` — смена `review_status`
        (`ready`/`rejected`), роль owner/admin;
      - `GET /api/recipes/{id}` — добавить в ответ `section`/`note`/
        `is_to_taste` ингредиентов (после TZ-M2R они есть в БД).
- [x] **A5. Производительность:**
      - кэшировать `ProductMatcher` в памяти процесса с TTL 10 минут
        (инвалидация по max(`observed_on`) истории цен) — убирает полный скан
        каталога на каждое открытие рецепта (`database.py:399,595`);
      - `planner_data`: `WHERE review_status = 'ready'` + LIMIT 500;
      - дашборд: убрать regex-`NOT EXISTS`-подзапросы (качество теперь в
        `review_status`), фронтенд не должен перезагружать дашборд после
        каждого действия;
      - `authenticate()`: обновлять `last_seen_at` не чаще раза в 5 минут
        (сравнение в SQL: `WHERE last_seen_at < now() - interval '5 minutes'`).
- [x] **A6. Безопасность:** `secrets.compare_digest` для CSRF
      (`database.py:172`); rate-limit на login (простой in-memory токен-бакет:
      5 попыток/минуту на IP+логин, 429 с Retry-After); `logout` без CSRF
      (достаточно валидной сессии); security-заголовки middleware
      (`Content-Security-Policy: default-src 'self'`, `X-Content-Type-Options:
      nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`);
      `recipe_detail` — явный список колонок вместо `r.*` (не отдавать
      `source_id`, `fingerprint`); `delete_inventory` — парсить счётчик DELETE;
      `add_inventory` — отклонять `expires_on` в прошлом (кроме флага
      `already_expired=true`).

## Часть Б — редизайн интерфейса

### Б1. Технический фундамент (сначала)

- [x] Разнести монолит: `static/css/tokens.css` (дизайн-токены),
      `static/css/base.css`, `static/css/components.css`,
      `static/css/views.css`; `static/js/` с ES-модулями
      (`api.js`, `state.js`, `render.js`, `views/*.js`). Без сборщика и npm —
      `<script type="module">`. Каждый файл — нормально отформатированный
      (никаких строк по 2000 символов).
- [x] Дизайн-токены: шкала отступов (4/8/12/16/24/32/48), шкала типографики
      (12/14/16/18/22/28/36), РОВНО два радиуса (8 и 16), палитра светлой и
      тёмной темы через CSS-переменные, `prefers-color-scheme` + ручной
      переключатель (сохранение в localStorage).
- [x] Шрифт: положить variable-шрифт Inter (woff2) в `static/fonts/` и
      подключить `@font-face` (сейчас Inter объявлен, но не загружается —
      все видят Segoe UI). Либо осознанно перейти на системный стек и убрать
      Inter из объявлений. Заголовки — тем же шрифтом; Georgia убрать.
- [x] Dev-режим: в `docker-compose.yml` смонтировать
      `./app/web/static:/app/app/web/static:ro` в сервис `web` — правки CSS/JS
      без rebuild; убрать ручные `?v=...` кэш-бастеры, вместо них
      `Cache-Control` уже есть.
- [x] Роутинг по hash (`#/plan`, `#/recipes`, `#/recipes/42`) — Back/Forward
      работают, диалог рецепта открывается по прямой ссылке.
- [x] Единые состояния: каждый экран имеет loading (скелетон), empty
      (объяснение + действие), error (встроенная плашка с «повторить», не
      исчезающий тост). Тост — только для подтверждений действий.
- [x] Доступность: aria-current на навигации, role/aria-selected на табах,
      aria-label на кнопках-иконках, фокус-ловушка в диалоге, контраст ≥ 4.5:1
      (заменить `.eyebrow #b8d9cb` и `.optional #8a8d88`), `prefers-reduced-motion`.
      Иконки — inline-SVG вместо текстовых глифов `⌂ ▦ ◫`.

### Б2. Экраны: сейчас → должно быть

**Рецепты** (главная боль):

- Сейчас: карточка = название + «N ингредиентов · M этапов» + «Стр. 12» +
  ярлык «нужна проверка» у 100% (`app.js:130`); ингредиенты видны только в
  диалоге, количество набрано мельче названия, под каждым — серая строка
  Ленты, секций нет.
- Должно быть:
  - карточка: название, 4–6 первых ингредиентов строкой («рис, бамия, томаты,
    лук…»), время (если есть), порции, бейдж кухни только если определена;
    бейдж «черновик» только у `needs_review`;
  - деталь рецепта: ингредиенты таблицей «количество+единица | продукт |
    примечание», сгруппированной по `section` с подзаголовками; количество
    визуально не мельче названия; цена Ленты — по явному переключателю
    «показать цены», не по умолчанию;
  - шаги — нумерованный список с нормальным межстрочным интервалом;
  - фильтры: поиск live с debounce 300 мс (без кнопки «Найти»), выбор типа
    приёма пищи и кухни чипами, переключатель «только готовые»;
  - пагинация «показать ещё» + счётчик результатов;
  - для owner/admin: кнопки «Готов»/«Отклонить» (A4) прямо в детали — очередь
    проверки из TZ-M2 §2.9.
- Приёмка: склеенного текста нет; любой рецепт открывается по прямой ссылке;
  смена статуса мгновенно отражается в списке.

**План питания:**

- Сейчас: форма + один «последний план»; при ошибке экран пустеет; блюдо
  нельзя заменить; список покупок — блоб через « · » в `<small>` (1961 символ
  шаблона, `app.js:160`).
- Должно быть:
  - история планов списком (A4), активный план — по умолчанию последний;
  - дни — колонками/карточками: завтрак/обед/ужин, у блюда — порции и ккал
    (или честное «нет оценки»);
  - кнопка «заменить блюдо» у каждого слота (эндпоинт из TZ-M5R; до его
    появления — disabled с подсказкой);
  - список покупок — таблица: чекбокс «куплено» (A4), продукт, количество,
    покрытие из запасов, товар Ленты и цена отдельной колонкой; группировка
    по категориям; итог суммы внизу;
  - предупреждение бюджета — плашкой над списком, не текстом в шапке.
- Приёмка: план не исчезает после F5 (A1); отметки «куплено» переживают
  перезагрузку; пустое состояние объясняет, что сделать.

**Сегодня (дашборд):**

- Сейчас: 4 счётчика, «холодильник» показывает только число истекающих.
- Должно быть: ближайшие приёмы пищи из активного плана с переходом к рецепту;
  список истекающих запасов ПОИМЁННО (название + срок) с переходом в Запасы;
  один CTA «Составить меню». Убрать счётчики «Источников»/«Товаров Ленты» —
  это служебная информация, ей место в «Настройках → Данные».

**Запасы:**

- Сейчас: « · »-строки, native confirm() на удаление.
- Должно быть: таблица (продукт, количество, место хранения, срок годности с
  цветовой градацией «истекает ≤3 дней»), сортировка по сроку; удаление с
  undo-тостом вместо confirm(); быстрые пресеты частых продуктов.

**Настройки:**

- Сейчас: правила питания схлопываются в `exclude+is_hard` при каждом
  сохранении; люди пересоздаются с новыми UUID.
- Должно быть: редактирование людей по одному (PATCH, стабильные id);
  правила — список с типом (аллергия/непереносимость/исключение/не любит) и
  флагом «строгое»; техника — та же сетка чекбоксов; отдельная секция «Данные»
  (счётчики источников/товаров, ссылка на очередь проверки рецептов).
- Требует: `PATCH /api/settings/people/{id}`, `PUT` больше не пересоздаёт
  людей заново (бэкенд-часть — сюда же).

**Продукты «Ленты»:** нормальная пагинация, показ КБЖУ из карточки (данные
уже приходят и выбрасываются), фильтр «только со скидкой».

**Авторизация:** оставить сплит-экран, но привести к новой типографике/токенам;
инлайн-ошибки полей; показывать требования к паролю до отправки.

### Б3. Что НЕ делать

- Не тянуть фреймворки (Vue/React) и сборщики — vanilla ES-модули достаточно;
  решение зафиксировано, чтобы не менять деплой (TZ-v2 допускает и Vue 3, но
  это отдельное решение пользователя).
- Не переделывать алгоритм планировщика (TZ-M5R).
- Не добавлять внешние CDN (шрифты/иконки — только локально): приложение
  локальное и должно работать без интернета.

## Приёмка всего ТЗ

1. `python -m unittest discover -s tests -v` — зелёные, включая новые тесты
   части А (TZ-TESTS §3).
2. `docker compose up -d db web` → регистрация нового пользователя → без
   настройки техники генерируется план (A2), после F5 план на месте (A1).
3. В списке рецептов видны ингредиенты; в детали — таблица с секциями; ни
   одной « · »-строки со склеенными фактами на экранах Запасы/Покупки.
4. Lighthouse (или ручная проверка): контраст AA, навигация с клавиатуры,
   Back работает, тёмная тема переключается.
5. Правка styles.css видна по F5 без rebuild контейнера (dev-том).
6. `curl -I localhost:8080` показывает CSP/XCTO/XFO-заголовки (A6).
