## 0. Сводка

Сейчас планировщик — честный оптимизатор, но **безличный**: он не знает, что
семья ела на прошлой неделе, что́ заменяли, кому что нельзя, сколько времени
есть на готовку в среду, что сейчас сезон кабачков и что одна пачка сметаны
закрывает три блюда. Это ТЗ превращает его в персональный: планировщик
строит **профиль вкуса семьи**, учитывает **каждого едока отдельно**,
понимает **контекст дня и сезона**, считает **реальные упаковки на весь
горизонт** и **объясняет** каждый выбор.

Что получает пользователь:

| Было | Станет |
|---|---|
| Кухни, бюджет, стратегия вводятся каждый раз | Профиль планирования семьи хранится; форма предзаполнена |
| Звёзды влияют линейно на одно блюдо | Вкус обобщается на тип блюда, кухню, ингредиенты; замены и «приготовлено/пропущено» тоже учатся |
| Прошлые планы забыты | Ротация: то, что ели в последние 3 недели, уходит вниз; любимое возвращается раз в неделю |
| Одна калорийность «на семью» | Цель по ккал и БЖУ у каждого; распределение по приёмам; аллергия «только у ребёнка» |
| Время готовки игнорируется | Будни/выходные, лимит минут на приём, «быстрый ужин» |
| Цена по книжной порции, каждое блюдо отдельно | Цена на семью, целые пачки на весь горизонт, переиспользование продуктов, штраф за порчу остатка |
| «Почему это блюдо?» — нет ответа | Каждый слот несёт 1–3 причины на человеческом языке |

Всё без LLM в runtime (решение TZ-v2 §3): только SQL, арифметика и CP-SAT.

fat_g, carb_g, by_meal)`:

- взрослый: Миффлин–Сан-Жеор при известных `sex/height/weight/birth_date`,

- ребёнок: таблица `CHILD_KCAL_NORMS` в `profile.py` (0–3: 1200, 4–6: 1500,
  7–10: 1800, 11–13: 2200, 14–17: 2500 — константы с указанием источника в
  комментарии; уточнение источника не блокирует реализацию); без даты
  рождения — 1400 как сейчас;
- `by_meal` — цель приёма = цель дня × `meal_shares[meal]`, только для
  приёмов из `eats_meals`.

Семейная цель слота `(d, m)` = Σ по людям, у которых `m ∈ eats_meals`.
`desired_servings` для слота — Σ `portion_factor` **только этих людей**
(сейчас считается по всем — `scaling.py:14`). Это меняет число порций для
семей, где кто-то обедает не дома: пометить в UI формы «кто ест дома».

### 3.2 Личные правила питания

`app_core.dietary_rules`: добавить `person_id UUID NULL REFERENCES people(id)
ON DELETE CASCADE` (NULL = вся семья, как сейчас) и `diet_tag TEXT NULL`
(вегетарианство/пост/без свинины — как теги из `recipes.diet_tags`).

Семантика в планировщике:

- жёсткое правило любого человека, который **ест этот приём** (`eats_meals`),
  — жёсткий запрет блюда в слоте (готовим одно на всех, TZ-v2 §10); если
  человек не ест приём дома, его правило на слот не действует;
- `dislike` конкретного человека — штраф, взвешенный (§6.1) долей ингредиента
  в блюде и «весом» человека (`portion_factor`);
- `diet_tag` — жёсткий фильтр по `recipes.diet_tags` (`vegetarian`, `lean`,
  …): блюдо должно нести тег для каждого едока слота с таким требованием;
  при отсутствии подходящих кандидатов слот получает предупреждение
  `diet_conflict`, а не молча игнорируется.

### 3.5 Календарь и время готовки

`context.py:day_context(date) -> DayContext(weekday: bool, holiday: bool,
season: str)`; праздники — производственный календарь РФ константой в коде
на текущий и следующий год (`HOLIDAYS_RU`), без внешних сервисов.

Рецепт получает `time_total_minutes` в пул (P5). Жёсткий фильтр слота:
`time ≤ limit(slot)`, где лимит из профиля §3.4; рецепты без времени

признак `time_unknown`. Если после фильтра в слоте < 8 кандидатов — лимит
слота удваивается, слот получает предупреждение `time_limit_relaxed`.

### 3.6 Сезон

`context.py:SEASONAL_INGREDIENTS: dict[month → set[canonical]]` — ~60
позиций для средней полосы (июнь–сентябрь: кабачок, огурец, клубника, укроп,

вкуса/разнообразия, не для экономии.

### 3.7 История и ротация

`context.py:history(household_id, starts_on)` читает `plan_meals` за
последний 21 день **до** `starts_on` (включая другие планы), плюс события
вкуса (§4). Выход: `last_seen[recipe_id] → дней назад`,
`recent_dish_types`, `recent_main_ingredients`.

Мягкий член (§6.1): `recency_penalty(r) = max(0, 21 − last_seen) / 21` —
блюдо, что ели вчера, получает полный штраф, через три недели — ноль.
Любимые блюда (аффинити ≥ 0.8) — исключение: штраф действует только 6 дней
(«любимое — раз в неделю»).

### 4.2 Аффинити

`taste.py:TasteModel.fit(events, recipes) -> Affinities` считает четыре
уровня, каждый — сглаженное среднее с затуханием:

```
score(key) = Σ value_i · decay(age_i) / (Σ decay(age_i) + K_PRIOR)
decay(age) = 0.5 ** (age_days / HALF_LIFE)           HALF_LIFE = 90 дней
K_PRIOR = 2 (рецепт), 4 (тип блюда), 6 (кухня), 6 (ингредиент)
```

Уровни: `recipe[recipe_id]`, `dish_type[code]`, `cuisine[code]`,
`ingredient[canonical]` (по главному и двум следующим по массе ингредиентам
рецепта, вес 1.0 / 0.5 / 0.5). Событие по рецепту распространяется на его
тип, кухню и ингредиенты с коэффициентом 0.5.

Итог для рецепта в слоте:

```
affinity(r) = clamp(
    recipe[r]                                  если есть ≥ 1 событие,
    иначе 0.6·dish_type[t] + 0.25·cuisine[c] + 0.15·mean(ingredient[...]),
  −1, +1)
```

Диапазон [−1, +1]; 0 — нет информации. Значения хранятся в
`app_core.taste_affinities(household_id, level, key, score, events_count,
updated_at)` и пересчитываются: (а) ночным джобом в `scheduler` для всех
семей; (б) инкрементально в том же запросе, что создал событие (одно
обновление строки рецепта + его типа/кухни/ингредиентов — дёшево).

### 4.3 Семейный компромисс

Если есть события с `person_id`, аффинити считается по людям слота и
сводится по правилу «среднее минус страдание»:

```
family_affinity = mean_p(aff_p · w_p) − λ · max(0, −min_p aff_p)
w_p = portion_factor_p / Σ portion_factor,  λ = 0.5
```

Блюдо, которое один член семьи откровенно не любит (aff ≤ −0.5),
проигрывает нейтральному даже при восторге остальных. Без личных событий
(нынешняя ситуация: рейтинг на семью) формула вырождается в семейный аффинити.

### 4.4 Холодный старт: онбординг вкуса

Новой семье и семье с < 10 событиями показывается «Выберите, что вы любите»:
20 карточек (`GET /api/taste/onboarding` → выборка: по 2 рецепта на каждую
из 10 самых частых пар (кухня, тип) среди `ready`, детерминированно по
`household_id`), пользователь отмечает любимое / не моё / пропуск;
`POST /api/taste/onboarding` пишет события `onboarding_like/skip`. В боте —
карточки с кнопками 👍 / 👎 / ⏭ (M7). Онбординг пропускаемый; он не
блокирует генерацию.

### 4.5 Новизна

`novelty` из профиля §3.4 задаёт долю слотов, в которых рецепты без событий
(`affinity == 0` от отсутствия данных) не получают штрафа неизвестности:
`low` — 10 %, `medium` — 30 %, `high` — 60 %. Реализация: мягкий член
`W_UNKNOWN · Σ x[r] · unknown(r)` плюс жёсткое ограничение сверху
`Σ unknown ≤ ceil(novelty_share · slots)`. Это гарантирует, что семья с
большой историей не застрянет на 15 блюдах, а новичку не выдадут сплошь
неизвестное.

## 6. Оптимизация

### 6.1 Признаки на (рецепт, слот)

`features.py:FeatureVector` (расширение `CandidateScore`, `candidates.py:150`):

| Признак | Диапазон | Источник |
|---|---|---|
| `cost_private_kop`, `need[p]` | ≥ 0 | стоимость ингредиентов **на семью** (× `recipe_scale`, P6), запасы вычитаются по количеству (FEFO, как в `shopping.py`), не «бесплатно целиком»; разделение на «личные» товары и потребность в общих — §6.3 |
| `kcal`, `protein_g`, `fat_g`, `carb_g` | ≥ 0 | как сейчас, × scale |
| `affinity` | [−1, 1] | §4 |
| `unknown` | {0,1} | нет событий вкуса |
| `dislike_penalty` | [0, 1] | Σ по нелюбимым ингредиентам едоков слота: доля массы ингредиента в блюде × `w_p` (P10) |
| `expiry_bonus` | [0, n] | как сейчас, но по количеству: min(нужно, есть) |
| `recency_penalty` | [0, 1] | §3.7 |
| `time_minutes`, `time_unknown` | | §3.5 |
| `season_bonus` | [0, 1] | §3.6 |
| `protein_base` | {meat, poultry, fish, eggs, dairy, legumes, veg} | по главному ингредиенту через `ingredient_synonyms.kind='group'` — добавить группы в засев |
| `cuisine_bonus`, `meal_fit`, `meal_bias`, `draft`, `dish_type`, `main_ingredient` | | как сейчас |

`slot_coefficient` (`optimizer.py:66`) переписывается через `WeightProfile`:

```
coef = W.cost · cost_private_rub
     + W.dislike · dislike_penalty
     − W.waste · expiry_bonus
     − W.cuisine · cuisine_bonus
     − W.taste · affinity                     # заменяет rating_bonus
     + W.unknown · unknown
     + W.recency · recency_penalty
     + W.time · max(0, time − soft_limit)/15  # мягко выше лимита профиля
     + W.time_unknown · time_unknown
     − W.season · season_bonus
     − W.fit · (meal_fit + meal_bias)
```

`rating_bonus` не удаляется из данных, но в коэффициент больше не входит —
звёзды теперь идут через события вкуса (А3).

### 6.2 Модель CP-SAT — назначения

Переменные и ограничения TZ-M5R §2.3 сохраняются (`x`, `empty`, `usage`,
повторы, `dish_type_cap`, соседние дни). Добавляется:

- **слоты по профилю**: планируются только `meals` из §3.4; слот без едоков
  (`eats_meals`) не создаётся;
- **калории и БЖУ по слоту**: для каждого `(d, m)` цель = Σ по едокам
  `by_meal[m]`; мягкое отклонение вне коридора ±15 % (`kcal_over/under`, как
  сейчас по дню, теперь по слоту) и по дню ±10 %; для белка — только
  недобор: `W_PROTEIN · max(0, target_protein_d − Σ protein)`; жиры/углеводы
  — информационно (в отчёт), без члена в целевой (первая версия);
- **разнообразие белковой базы**: `Σ_d [protein_base(d, dinner) = b] ≤
  ceil(days / 3) + 1` жёстко для `meat`/`poultry`/`fish` при `days ≥ 5`;
  для остальных — мягкий штраф `W_VARIETY` за повтор базы в соседние дни
  (расширение нынешнего `repeat` по главному ингредиенту);
- **разнообразие кухонь** при `cuisine_mode = prefer`: мягкий штраф
  `W_VARIETY` за третью подряд одинаковую кухню в ужинах;
- **остатки «на два раза»** (`allow_leftovers`): для ужинов переменная
  `left[r, d] ∈ {0,1}` — «блюдо r, приготовленное в `(d, dinner)`, съедается
  в `(d+1, lunch)`». Ограничения: `left[r,d] ≤ x[r,d,dinner]`,
  `Σ_r x[r,d+1,lunch] + Σ_r left[r,d] + empty[d+1,lunch] = 1`. Потребность
  в продуктах ужина-источника ×2 (§6.3), время готовки обеда 0, `recency` не
  штрафуется, `dish_type_cap` считает один раз. Мягкий бонус `W_LEFTOVER` за
  экономию времени в будни; не более `ceil(days/3)` таких пар за горизонт.
  Допускаются только `dish_type ∈ LEFTOVER_FRIENDLY` (суп, рагу, плов,
  запеканка, паста, котлеты… — константа в коде). В плане слот помечен
  `leftover_of: meal_id`, покупки на него не дублируются, порции ×2 у
  ужина-источника;
- **новизна**: `Σ x·unknown ≤ ceil(share · slots)` (§4.5).

### 6.3 Модель CP-SAT — упаковки и остатки

Главный экономический эффект: солвер видит **целые пачки на весь горизонт**.

`packs.py:build_pack_model(candidates_by_slot, matcher, inventory)`:

1. Для каждого кандидата и каждого ингредиента — сопоставленный товар
   `p` (как сейчас через `ProductMatcher`) и потребность `need[r, p]` в
   базовых единицах на семью.
2. Множество товаров `P` — объединение по всем кандидатам горизонта. Товары,
   встречающиеся только у одного кандидата, упаковками не моделируются — их
   стоимость (целыми пачками) входит в `cost_private_kop`; это ограничивает
   размер модели. **Общие товары** (встречаются у ≥ 2 кандидатов)
   моделируются:
   - `n[p] ∈ [0, N_MAX]` — число пачек;
   - `n[p] · pack_size[p] + stock[p] ≥ Σ_{r,d,m} x[r,d,m] · need[r,p]`;
   - стоимость `Σ n[p] · price[p]` входит в целевую с весом `W.cost`;
   - остаток `left[p] = n[p]·pack_size + stock − Σ need` и штраф
     `W.leftover_waste · left[p] · perish[p] · price_per_unit[p]`, где
     `perish ∈ {0 (крупы, масло, консервы, заморозка), 0.5 (сыр, овощи),
     1.0 (молочка, зелень, охлаждённое мясо)}` по `category_slugs` товара —
     таблица в `packs.py`. Это ровно требование TZ-v2 §10: «нулевой остаток
     не всегда оптимален; штраф зависит от срока, стоимости и объёма».
3. `N_MAX = ceil(max_need / pack_size) + 1`.

Ограничение размера: если общих товаров > 120 или переменных > 20 000 —
берутся 120 самых дорогих по суммарной потребности, остальные — как «личные»;
план получает `warnings: pack_model_truncated`. Бюджет теперь считается по
`Σ n[p]·price + Σ x·cost_private`, что совпадает с итогом списка покупок с
точностью до округлений — расхождение сейчас (модель считает «книжную» цену,
список — пачки на семью) исчезает.

`shopping.py` после решения использует `n[p]` из решения как подсказку, а не
пересчитывает с нуля: `build_shopping(..., pack_hint=solution.packs)`;
при расхождении > 1 пачки — логировать (`planner.pack_mismatch`).

### 6.5 Лимиты

- `MAX_CANDIDATES_PER_SLOT` остаётся 40; при `days > 7` — 30;
- лимит решателя `min(10 + 2·days, 30)` секунд, `relative_gap` 2 %;
  двухнедельный план с упаковками должен укладываться в 30 с при тёплом
  кэше — критерий приёмки;
- если модель с упаковками не даёт FEASIBLE за лимит — повтор **без**
  упаковок (нынешняя модель), предупреждение `pack_model_skipped`; затем —
  жадный fallback как сейчас.

### 6.6 Замена блюда

`slot_alternatives` (`planner.py:1304`) использует те же `FeatureVector` и
`slot_coefficient`; дополнительно:

- альтернативы группируются: 4 «похожих» (тот же `dish_type` или
  `protein_base`), 4 «других» (разные типы, круговой обход как сейчас),
  2 «новых» (`unknown = 1`); при нехватке группы добираются из соседних;
- каждая несёт `reasons` (§5) и дельту к бюджету/ккал дня относительно
  текущего блюда;
- при применении замены `replace_meal` пишет события вкуса (§4.1) и
  пересобирает покупки с `pack_hint = None` (полный пересчёт, как сейчас).

## 9. Приёмка

### 9.1 Функциональная

1. Семья из 2 взрослых + ребёнок с аллергией на орехи у ребёнка (правило с
   `person_id`) и `eats_meals` без обеда у одного взрослого: обеды не содержат
   орехов, порции обеда считаются по двум едокам, ужин — по трём.
2. План на 7 дней: ни одно блюдо из планов предыдущих 14 дней не повторяется
   в первые 3 дня, кроме блюд с аффинити ≥ 0.8.
3. После двух замен супа-пюре на борщ следующая генерация ставит борщ выше
   супа-пюре в одинаковых условиях (аффинити типа/рецепта).
4. `mode = quick`: все будние ужины ≤ `weekday_max_minutes` либо слот несёт
   `time_limit_relaxed`.
5. `allow_leftovers = true`, 7 дней: не более 3 пар «ужин → обед», у
   обеда `leftover_of`, покупки не дублируются, время готовки 0.
6. Упаковки: для плана с ≥ 2 блюдами на сметане список покупок содержит
   одну пачку, если её хватает; итог списка совпадает с `estimated_cost` плана
   с точностью до 1 %.
7. Каждый слот несёт ≥ 1 причину; альтернативы — по одной.
8. Двухнедельный план на живых данных при тёплом кэше — ≤ 30 с.

### 9.2 Офлайн-оценка качества

`scripts/eval_planner.py` на живой БД, для каждой семьи с историей:

- **novelty@7**: доля блюд плана, не встречавшихся за 21 день; цель ≥ 60 %
  при `medium`;
- **taste@7**: средний `affinity` выбранных блюд против случайного
  допустимого набора; цель — выше на ≥ 0.2;
- **cost/kcal**: стоимость плана на 1000 ккал — не хуже M5R более чем на 5 %
  в `balanced` и лучше на ≥ 10 % в `economy`;
- **protein_gap**: доля дней с недобором белка > 20 % — ≤ 10 % в `fitness`;
- **stability**: одна и та же семья и дата → одинаковый план (детерминизм
  `random_seed`, `stable_tiebreak`).

Результаты — в отчёт `ТЗ/REPORT-<дата>.md` с таблицей до/после.

## 10. Не входит

- LLM в runtime (описания «почему» — шаблоны, не генерация);
- медицинские диеты и лечебные назначения (TZ-v2 §12);
- несколько магазинов, доставка;
- автоматическое распознавание чеков/холодильника;
- обучение на чужих семьях (коллаборативная фильтрация) — только своя
  история; вернуться, когда семей > 20.

## 11. Зафиксированные допущения (для ревью владельца)

- А1. Готовим одно блюдо на всех едоков слота; «отдельная тарелка» для
  человека не планируется. Личные правила действуют жёстко на слот.
- А2. Кухни по умолчанию становятся **мягким** предпочтением (`prefer`);
  нынешнее жёсткое поведение («пул добирает выбранные кухни», решение
  18.08.2026) доступно как `only`.
- А3. Звёзды переезжают в события вкуса; старые оценки мигрируют событиями
  `rated` с датой `updated_at`.
- А4. Горизонт до 14 дней; форма веба показывает 1/3/5/7/14.
- А5. Праздники и сезонность — константы в коде, без внешних сервисов.
- А6. Детские нормы — константы с указанием источника в коде.
- А7. Режимы (`economy/balanced/variety/fitness/quick`) заменяют в форме
  стратегию «Экономно/Сбалансированно/Премиально»; «Премиально» остаётся
  переключателем выбора товаров внутри формы, а не режимом.
