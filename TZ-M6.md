# ТЗ M6 — Веб-интерфейс (React SPA) + API-соглашения

## Цель
Единый локальный веб-интерфейс всей системы: от мастера первого запуска и анкет
семьи до генерации плана, списка покупок и админки матчинга. SPA на React поверх
REST API. Авторизации нет — приложение живёт только в локальной сети.

## Зависимости
M1 (каркас API). Страницы подключаются по мере готовности M2–M5;
каркас интерфейса (навигация, «Семья») можно поднимать сразу после M1.
Страницы «Дневник» и «Аналитика» реализуются в M7 (здесь — только пункты навигации).

## Состав работ

### 1. Инфраструктура фронтенда (`web/`)
- Vite + React 18 + TypeScript (strict).
- Библиотеки: react-router (маршруты), TanStack Query (запросы, кеш,
  инвалидация), Mantine (UI-компоненты, формы, тёмная тема),
  Recharts (графики — используются в M7).
- Типы API из OpenAPI: `npm run gen:api` → openapi-typescript читает
  `http://localhost:8000/openapi.json` → `src/api/schema.d.ts`; поверх — тонкий
  типизированный fetch-клиент. Правило: изменил API — перегенерируй типы;
  проверка «`gen:api` не даёт диффа» входит в чек-лист каждого модуля.
- Структура: `src/pages/`, `src/components/`, `src/api/`. Интерфейс на русском;
  все строки — в общем модуле (задел на локализацию).

### 2. Сборка и раздача
- Dev: `npm run dev` (Vite, порт 5173), proxy `/api` → `http://localhost:8000`.
- Prod: multi-stage Dockerfile — стадия `node:22-alpine` собирает `web/dist`,
  статика копируется в Python-образ; FastAPI раздаёт её (StaticFiles) с
  SPA-fallback: любой путь кроме `/api/*`, `/docs`, `/health` → `index.html`.
- Публикация порта — см. M1: по умолчанию `127.0.0.1:8000`, при `WEB_EXPOSE=1`
  доступ из домашней сети; вёрстка обязана быть удобной с телефона (адаптив).

### 3. Страницы
- **Каркас**: сайдбар-навигация, общий layout, страница ошибки,
  состояния загрузки (скелетоны Mantine).
- **Мастер первого запуска**: если семьи в БД нет — визард: название семьи →
  члены семьи (профили M4) → переход на дашборд.
- **Дашборд**: блюда сегодняшнего дня активного плана (кнопки «съедено» — M7);
  статус системы: свежесть цен по каждому магазину (последние успешные
  `parse_runs`), доступность Ollama, число товаров в очереди матчинга; быстрые действия
  («создать план», «список покупок»).
- **Семья**: карточки членов, формы профилей, расчётные нормы из M4
  (TDEE, распределение по приёмам), restrictions (аллергии/дизлайки тегами).
- **Рецепты**: поиск M2 (строка запроса + фильтры: тип приёма, ккал/порция,
  `cook_minutes`, исключить ингредиенты); карточка рецепта: ингредиенты
  с граммовками, шаги, КБЖУ на порцию (M4), похожие (`find_similar`);
  режим «что приготовить из холодильника» — подбор рецептов по текущим
  остаткам (`include_ingredients` из `fridge`).
- **Планирование** — мастер из 3 шагов:
  1. Параметры: дни (3/4), бюджет, приёмы пищи, исключения; пожелания —
     свободный текст (парсит LLM M5) и/или контролы (работает без LLM).
  2. Сетка день×приём: КБЖУ по каждому едоку, кнопки «заменить блюдо»
     (запасные кандидаты + `find_similar`) и «убрать»; текст-объяснение
     плана (если LLM включён). Прогресс генерации — этапы
     (подбор блюд → расчёт порций → оптимизация закупки).
  3. Закупка: сравнение корзин по магазинам («Лента 2 840 ₽ /
     Пятёрочка 3 105 ₽»), выбран рекомендованный (дешевле целиком) — можно
     переключить; список покупок с ценами и суммой, прогноз излишков;
     кнопка «Подтвердить план» → status=active.
- **Покупки**: чек-лист активного плана (в шапке — магазин закупки),
  группировка по категориям товаров;
  отметить куплено + фактическая цена (по умолчанию из каталога,
  оптимистичное обновление); «добавить не из плана» — поиск по каталогу
  `store_products` (запись в expenses и fridge — механика M7).
- **Холодильник**: таблица остатков (ингредиент, граммы, годен до), CRUD;
  подтверждение прогноза остатков после готовки.
- **Админ**: очередь матчинга M3 (пары товар↔ингредиент с confidence,
  кнопки да/нет/выбрать ингредиент вручную); журнал `parse_runs`;
  карантин рецептов M2; кнопка «запустить парсинг сейчас».

### 4. API-соглашения (бэкенд-часть модуля)
- Все роуты — `/api/v1/*`, pydantic-схемы на вход/выход, OpenAPI-теги по модулям.
- Единый формат ошибок `{error: {code, message}}` (обработчик из M1).
- `GET /api/v1/system/status` — свежесть цен, последний прогон, доступность
  Ollama (для дашборда).
- `POST /api/v1/admin/parse-now` — ручной запуск парсинга (фоновая задача).
- Swagger UI `/docs` — автодокументация API из OpenAPI-схемы.

### 5. Документация
- `docs/web.md` + `docs/web.ru.md`: устройство фронтенда, генерация типов,
  как добавить страницу; скриншоты основных экранов.

## Критерии готовности
- [ ] Полный цикл в браузере без консоли разработчика: первый запуск → семья →
      генерация плана → замена блюда → подтверждение → покупки с фактическими
      ценами → холодильник пополнился.
- [ ] `npm run gen:api` воспроизводит типы без диффа; `tsc --noEmit` чисто.
- [ ] Прод-образ: `docker compose up -d` → SPA на `localhost:8000`,
      `/docs` работает.
- [ ] При недоступном Ollama мастер планирования полноценно работает
      в кнопочном режиме, статус честно виден на дашборде.
- [ ] С телефона по домашней сети (`WEB_EXPOSE=1`) интерфейс удобен.
