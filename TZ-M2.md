# ТЗ M2 — База рецептов + RAG

## Цель
Наполнить БД рецептами с граммовками, посчитать эмбеддинги, построить
гибридный поиск (SQL-фильтры + векторная близость). Это учебное ядро RAG.

## Зависимости
M1 (схема БД, таблицы `recipes`, `ingredients`, `recipe_ingredients`).

## Состав работ

### 1. Парсер сайта рецептов (`scripts/import_recipes.py`)
Источник: povarenok.ru или eda.ru (выбрать по итогам разведки — у кого
стабильнее вёрстка и полнее граммовки; начать с povarenok — проще HTML).

- httpx + selectolax/BeautifulSoup, задержка 2–3 сек между запросами,
  User-Agent обычного браузера, уважение robots.txt.
- Обход по категориям: завтраки, супы, вторые блюда, гарниры, салаты, детское.
- Целевой объём первой загрузки: **3–5 тыс. рецептов** (не гнаться за всем сайтом).
- Из каждого рецепта извлечь: название, ингредиенты с количествами, шаги,
  количество порций, категорию, время приготовления (`cook_minutes`, если
  указано на странице), способ приготовления (эвристикой по шагам:
  «обжарить» → fry, «варить» → boil...).
- Сырые страницы кешировать на диск (`data/raw/`), чтобы перезапуск парсера
  не ходил в сеть повторно.

### 2. Нормализация ингредиентов — самая важная часть
Проблема: «филе куриное», «куриная грудка», «грудка цыплёнка» — один ингредиент.

Пайплайн нормализации:
1. Приведение единиц к граммам: «2 шт яйца» → 110 г (справочник средних весов
   штучных продуктов: яйцо 55 г, луковица 80 г, картофелина 100 г, зубчик
   чеснока 5 г, ст.л. 18 г, ч.л. 5 г, стакан 200 мл — таблица в коде/БД).
2. Лемматизация + чистка («св.», «охлажд.», бренды — выкинуть).
3. Поиск существующего ингредиента: точное имя → эмбеддинг-близость
   (cosine > 0.85) → иначе создать новый.
4. Рецепты, где не удалось нормализовать >30% ингредиентов, — в карантин
   (таблица не нужна, флаг/лог), не в основную базу.

КБЖУ ингредиентов: взять открытую таблицу химсостава (USDA FoodData Central
или русскоязычные таблицы Скурихина) и одноразовым скриптом сматчить
с нашими ингредиентами; для не найденных — заполнить вручную топ-200
самых частых, остальные пометить `kcal_100 IS NULL` (планировщик их избегает).

### 3. Эмбеддинги
- Модель: `intfloat/multilingual-e5-small` (384 dim, CPU, ~120 МБ).
  Обёртка `app/recipes/embedder.py` c единственной функцией `embed(texts) -> list[vec]`;
  для e5 обязательны префиксы `query:` / `passage:`.
- Текст для эмбеддинга рецепта: `название + список ингредиентов + теги + тип блюда`.
  Шаги приготовления в эмбеддинг НЕ включать (шум).
- `scripts/backfill_embeddings.py` — пересчёт для всех записей без эмбеддинга
  (рецепты, ингредиенты; позже M3 использует его же для товаров).

### 4. Поиск (`app/recipes/search.py`)
Функция `search_recipes(query, filters, limit)`:
- filters: meal_type, max_kcal_per_serving, exclude_ingredients[],
  include_ingredients[], max_cook_minutes, tags.
- SQL: WHERE по фильтрам (жёсткие ограничения — аллергии реализуются ТОЛЬКО
  здесь, никогда через векторную близость!) + ORDER BY cosine distance к
  эмбеддингу запроса, LIMIT.
- Отдельная функция `find_similar(recipe_id)` — для «замени это блюдо».
- REST: `GET /api/v1/recipes/search`, `GET /api/v1/recipes/{id}`.

### 5. КБЖУ рецепта
`app/recipes/nutrition_calc.py`: суммировать по `recipe_ingredients`
(граммы × КБЖУ/100 сырого), поделить на порции. Готовый вес порции —
через коэффициенты M4 (если M4 ещё нет — заглушка factor=1.0).
Кешировать в материализованное поле или считать на лету — на лету, объёмы малые.

## Критерии готовности
- [ ] В БД ≥3000 рецептов, ≥80% ингредиентных строк нормализованы.
- [ ] Топ-200 ингредиентов имеют КБЖУ.
- [ ] `search_recipes("лёгкий ужин из курицы", exclude=["рыба"])` возвращает
      релевантные рецепты без рыбы за <200 мс.
- [ ] Тест: рецепт с известным составом даёт ожидаемое КБЖУ ±2%.
- [ ] Повторный запуск импорта не создаёт дублей (идемпотентность по source_url).
