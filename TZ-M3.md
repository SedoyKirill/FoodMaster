# ТЗ M3 — Парсеры магазинов (Пятёрочка, Лента) + матчинг товар↔ингредиент

## Цель
Раз в сутки собирать актуальные каталоги выбранных магазинов — Пятёрочки и
Ленты (товары, цены, граммовки), вести историю цен и связывать товары
с ингредиентами рецептов. Несколько магазинов нужны планировщику M5, чтобы
сравнить стоимость корзины целиком и рекомендовать один магазин для закупки.

## Зависимости
M1 (таблицы `store_products`, `price_history`), M2 (эмбеддер, таблица ингредиентов).

## Архитектурный принцип
Код магазина — за интерфейсом `StoreAdapter` (`get_categories()`,
`get_products(category)`). Реализации v1: `FivekaAdapter` и `LentaAdapter`;
включённые магазины — список `STORES` в `.env`. Добавление Магнита потом —
новый адаптер, а не переписывание.

## Состав работ

### 1. Разведка API (первый шаг исполнителя!)
Каталоги с ценами у обеих сетей отдаются через внутренние API их сайтов/приложений:
- Пятёрочка: исторически эндпоинты вида
  `5d.5ka.ru/api/catalog/v2/stores/{store_id}/categories` и `.../products`.
- Лента: внутреннее API lenta.com (пути смотреть в DevTools → Network).

Актуальные пути ПРОВЕРИТЬ через DevTools — они периодически меняются.
- Найти `store_id` ближайших магазинов обеих сетей (выбор адреса на сайте →
  подсмотреть id в запросах). Записать в `.env` → `FIVEKA_STORE_ID`, `LENTA_STORE_ID`.
- Зафиксировать в `app/store/<store>/README.md`: эндпоинты, заголовки,
  формат ответа, примеры. Если API закрыто/капча — fallback-план: Playwright
  (реальный браузер в контейнере) для обхода страниц категорий; заложить это
  интерфейсом адаптера, реализовывать только там, где httpx-путь не взлетит.

### 2. Сборщик (`app/store/collector.py`)
- Запуск APScheduler'ом ежедневно в 03:00 (контейнер `scheduler`),
  последовательно по всем магазинам из `STORES`; таймаут — 1 час на магазин,
  отдельная запись `parse_runs` на каждый.
- Обход всех продуктовых категорий (бытовую химию и т.п. — исключить списком).
- Ограничение частоты: ≤1 запрос/сек, ретраи с экспоненциальной задержкой.
- Для каждого товара: upsert в `store_products` (по `external_id`),
  запись цены дня в `price_history` (цена + флаг промо).
- Извлечение граммовки: из поля API, если есть; иначе regex по названию
  («850г», «0,93л», «10шт»). Не распарсилось → `pack_grams NULL`
  (оптимизатор такие товары пропускает, лог для ручного разбора).
- Итог прогона — запись в `parse_runs` (status + stats: сколько товаров,
  сколько новых, сколько без граммовки, сколько ошибок). Последний прогон
  виден на дашборде и админ-странице M6; при падении дашборд показывает
  предупреждение «цены устарели от <дата>».

### 3. Матчинг товар → ингредиент (`app/store/matcher.py`)
Задача: «Филе грудки цыплёнка охл. 850г Красная Цена» → ингредиент «куриное филе».

Пайплайн (запускается после сборки для новых/несматченных товаров):
1. Чистка названия: убрать бренды (стоп-список пополняемый), «охл.», «зам.»,
   вес, проценты жирности.
2. Эмбеддинг очищенного названия → cosine к эмбеддингам ингредиентов.
3. Пороги: >0.88 — автоматически связать (`match_confidence`);
   0.75–0.88 — кандидат, в очередь ручного подтверждения (админ-страница
   «Матчинг» в веб-интерфейсе M6: пары, кнопки да/нет/выбрать вручную);
   <0.75 — не матчить.
4. Ручные правила-исключения в YAML (`app/store/match_rules.yaml`) для вечных
   ошибок эмбеддингов («крабовые палочки» ≠ «краб» и т.п.). Правила применяются
   ДО эмбеддинга и имеют приоритет.
5. Один ингредиент ↔ много товаров — это норма (разные упаковки/бренды).

### 4. API цен для планировщика (`app/store/prices.py`)
- `get_offers(ingredient_id, store) -> [Offer(product, pack_grams, price_kop, promo)]` —
  актуальные (сегодняшние/вчерашние) предложения по ингредиенту в конкретном
  магазине, отсортированные по цене за 100 г. Оптимизатор M5 вызывает по
  каждому магазину отдельно и сравнивает корзины целиком.
- `price_trend(product_id, days=30)` — для аналитики M7.

## Критерии готовности
- [ ] Ночной прогон стабильно собирает каталоги обоих магазинов
      (≥2000 продуктовых позиций каждый) и пишет историю цен; повторный
      запуск в тот же день не дублирует записи.
- [ ] ≥70% товаров продуктовых категорий имеют распарсенную граммовку.
- [ ] Топ-100 ингредиентов из рецептов имеют предложение хотя бы в одном
      магазине; ≥70 из них — в обоих.
- [ ] Матчинг: на ручной выборке из 100 товаров точность автоматических
      связок ≥90% (проверяется глазами один раз).
- [ ] Падение API одного магазина не роняет остальные сервисы и не мешает
      сбору второго; после 3 неудачных прогонов подряд планировщик честно
      говорит «цены устарели от <дата>».
