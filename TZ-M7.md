# ТЗ M7 — Дневник питания, финансы, аналитика

## Цель
Замкнуть цикл обратной связи: фиксировать, что реально съедено и потрачено,
сравнивать с планом и нормами, показывать аналитику (КБЖУ, деньги, цены,
излишки, вес). Вся математика детерминированная; LLM — только для разбора
свободного текста о еде (опционально, с ручным fallback).

## Зависимости
M1 (таблицы `meal_log`, `expenses`, `weight_log`), M3 (каталог товаров для
ручных покупок), M4 (КБЖУ, пересчёт готовое↔сырое), M5 (планы, LLM-протокол),
M6 (страницы «Дневник», «Аналитика», механика покупок).

## Состав работ

### 1. Дневник питания (`app/finance/diary.py`)
- Лог из плана: `POST /api/v1/diary/plan-meal` {plan_meal_id, member_id,
  eaten_fraction} → КБЖУ порции (M4/M5) × доля. UI: на дашборде и странице
  «Дневник» — блюда дня, кнопки «всё / ¾ / ½ / ¼ / свой %» по каждому едоку.
- Внеплановая еда свободным текстом («2 бутерброда с колбасой и чай с сахаром»):
  `LLMProvider.parse_food(text)` (протокол M5) → [{ингредиент, граммы,
  сырое/готовое}] → матчинг к `ingredients` (точное имя → эмбеддинг-близость) →
  пересчёт готовое→сырое (M4) → КБЖУ. Разбор показывается пользователю
  на подтверждение ДО записи (ингредиенты и граммы можно поправить).
- Без LLM (или разбор не удался / не подтверждён) — ручная форма:
  поиск ингредиента + граммы + переключатель «в сыром/готовом виде».
- Редактирование и удаление записей; ретро-ввод за прошлые даты.
- Свод дня по каждому члену семьи: Σ КБЖУ vs норма M4, остаток дневной нормы.

### 2. Финансы (`app/finance/expenses.py`)
- Автозапись из плана: отметка «куплено» в M6 (bought=true +
  actual_price_kop) → upsert в `expenses` (source=plan, привязка к plan_id).
  Правка цены корректирует запись.
- Ручная покупка из каталога: поиск по `store_products` → количество упаковок →
  цена подставляется из последней `price_history` (можно поправить) →
  `expenses` (source=manual) + пополнение `fridge` (pack_grams × количество),
  если товар сматчен с ингредиентом.
- Свободная трата: сумма + заметка, без привязки к товару
  (рынок, другой магазин).
- Месячный бюджет `families.month_budget_kop` (опционально): индикатор
  «потрачено из бюджета» на дашборде и в аналитике.

### 3. Дневник веса
- `POST /api/v1/members/{id}/weight` {date, weight_kg} → `weight_log` +
  обновление `family_members.weight_kg` (текущий вес); нормы M4
  пересчитываются автоматически (считаются на лету от профиля).
- График веса — в аналитике.

### 4. Аналитика (`app/finance/analytics.py`, страница M6, Recharts)
Все отчёты — SQL-агрегации (без LLM), эндпоинты `/api/v1/analytics/*`:
- **Питание**: факт vs норма КБЖУ по дням/неделям на каждого члена
  (бары + линия нормы); распределение по приёмам пищи.
- **Деньги**: траты по неделям/месяцам (из плана / ручные — раздельно);
  план vs факт по каждому плану закупки; индикатор бюджета.
- **Цены**: график `price_history` товара (`price_trend` из M3); сравнение
  цены ингредиента между магазинами; список «подешевело/подорожало»
  относительно последней покупки этого товара.
- **Излишки**: по завершённым планам — прогноз излишков vs подтверждённые
  остатки холодильника → «спасено / выброшено, г», динамика по планам.
- **Вес**: график `weight_log` по каждому члену семьи.

### 5. Будущие расширения (в v1 НЕ реализуются; архитектура не должна мешать)
- Импорт чеков: реквизиты QR (ФН/ФД/ФП) → API ФНС «Проверка чека» →
  построчный состав покупки → авто-матчинг к каталогу.
  Задел: `expenses.source=receipt` уже есть в схеме.
- Фото чека → vision-модель.
- Экспорт CSV (`meal_log`, `expenses`).

## Критерии готовности
- [ ] Блюдо из плана логируется за ≤2 клика; свод дня совпадает с ручным
      пересчётом (юнит-тест).
- [ ] Свободный текст: ≥16 из 20 контрольных фраз разбираются в разумные
      ингредиенты/граммовки (ручная проверка один раз); сбой разбора никогда
      не теряет запись — всегда доступен ручной fallback.
- [ ] Ручная покупка из каталога попадает в `expenses` И пополняет холодильник.
- [ ] Недельный отчёт для семьи из 3 человек сходится с ручной сверкой.
- [ ] Запись нового веса меняет результат `family_daily_needs` (тест).
- [ ] График цены строится для товара с ≥30 днями истории.
